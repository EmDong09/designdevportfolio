I designed an internal benchmarking dashboard that gives my team one shared place to test, store, grade and compare the After Effects motion design skills we’re building for an AI agent harness, so we can tell which skills are improving and why.

Background

Why

Adobe After Effects presented a steep learning curve for people new to motion design and video editing. Aspect, a collaborative video storage platform, contracted our team to build a lightweight AI agent harness intended to lower that barrier. The project aimed to expand Aspect’s business model beyond storage by adding editing capabilities to what it could offer its users.

Problem

Videos, prompts, token costs and quality scores were scattered across separate tools, making it difficult for our team to keep test runs organized, store and compare results, and systematically refine skills. We needed a shared workspace to evaluate results, track improvements and choose the best version of each skill.

Constraints

  • Dense data had to be accessible to a team with limited motion design knowledge.
  • Teammates needed to view and build on each other’s work.
  • The dashboard had to support single-skill, combined-skill and storyboard tests.
  • Uploading test details had to be straightforward, with clear guidance for each field.

Starting Point

Design goal

Make navigation and interactions intuitive, even when the dashboard presented a large amount of information.

Starting inputs

I gathered four inputs to establish the dashboard’s structure and visual direction:

  • A one-shot wireframe from my project manager as a starting point.
  • Dashboard UI references I curated online.
  • A screenshot of Aspect’s home page to guide the color palette and visual style.
  • A navigation flowchart I created to map pages, metrics, table content and the flow of information.

Tool choice

I combined these inputs and gave them to Claude, connected to Figma through Figma MCP. I chose this workflow rather than working exclusively in Claude so I could refine the design through either manual adjustments or prompts, while keeping the overall design easily accessible to my team throughout the build.

Design Iterations

Building from the first pass

The initial designs provided a useful skeleton, but the interactions were not yet defined. It was unclear whether clicking an element would open a pop-up or lead to another page. I spent the early part of the project mapping these interactions and designing each page and pop-up a user could encounter.

Refining the details

Once the core navigation was in place, I reviewed the dashboard page by page to refine the content, clarify interactions, and fill gaps in the user flow. This included the following changes:

  • Removed unnecessary subtext.
  • Reorganized card content to improve readability.
  • Removed visual elements that implied unsupported interactions.
  • Clarified layout across pages with large collections.
  • Removed redundant information to keep each page focused on its purpose.
  • Defined missing flows for editing data and deleting test runs.

Team feedback

I asked for my team’s feedback throughout the design process because they would use the dashboard internally. Their day-to-day use also served as a small-scale simulation of how the tool might be used if it were handed off to Aspect.

Making test run cards clearly clickable

Video thumbnails made the cards look like video players rather than entry points to run details. I added an interaction cue to make their clickability clearer.

Replacing skill pills with a drop-down

A row of individual skill filters took up too much space. I replaced the pills with a drop-down menu to reduce clutter.

Simplifying motion design terms

Motion design terms were unfamiliar to teammates who had not yet tested those skills. I added short, plain-language descriptions to make each skill easier to understand.

Keeping benchmarks in local testing

A software analyst pointed out that the team already ran benchmarks locally, so entering those results was more practical than rerunning checks in the dashboard. I reduced the upload flow from four steps to two: entering run details and local results, then reviewing and uploading.

Design Rationale

Consistent shapes made interactions predictable

I used pill shapes for single-click buttons and rectangles for search bars and drop-downs that offered multiple or open-ended choices.

Color carried meaning

  • Red — Warnings
  • Dark blue — Selected states and primary actions
  • Gray — Passive buttons
  • Green — Confirmations and checks

Dense tables were a deliberate tradeoff

I prioritized keeping key test run information visible in the tables. Requiring users to open each run for those details would have added friction, so I retained enough information to support skimming and tracking, even at the cost of a denser layout.
